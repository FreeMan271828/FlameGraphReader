# FlameReader

**一个用 Rust 写的高性能 SVG 火焰图查看器（Windows 桌面原生）。**

专门解决普通火焰图工具在**超大火焰图**上的痛点：浏览器打开一个百万帧级的 SVG 会卡死或长时间无响应，缩放/平移掉帧，切换文件要等重新解析。FlameReader 把整张图一次性解析成扁平的 GPU 友好结构，之后所有交互都只做视口裁剪，因此帧数与交互延迟基本解耦。

## 为什么浏览器会卡

火焰图 SVG 通常是 `flamegraph.pl` / `inferno` 之类的工具生成的，形态是：

```xml
<g><title>foo (1234 samples, 12.34%)</title>
   <rect x="..." y="..." width="..." height="15" fill="rgb(...)" rx="2" ry="2"/>
   <text x="..." y="...">foo</text></g>
```

也就是说，**每一帧就是一个 `<g>` + 一个 `<rect>` + 一个 `<text>`**。一个 500 万帧的火焰图会展开成 1500 万个 DOM 节点：

| 问题 | 原因 |
| --- | --- |
| 打开就卡 | XML 解析 + 建 DOM + 样式计算 + 布局，全部在主线程 |
| 缩放/平移掉帧 | 每一次视图变化都要重新布局 / 重绘上百万个元素 |
| 切换文件慢 | 每个文件都要重新走一遍上面的流程 |
| 内存暴涨 | 一个 SVG 元素在浏览器里的开销是数百字节量级 |

FlameReader 把「图形」和「文档」解耦：**解析一次，之后只做整数索引级的裁剪运算**。

## FlameReader 的做法

| 手段 | 效果 |
| --- | --- |
| 手写字节扫描器解析 SVG，丢弃 DOM，压成 32 字节/帧的扁平数组 | 解析吞吐 ~700–1100 MB/s |
| 行内按 x 排序 + 两层二分查找裁剪视口 | 单帧几何构建 O(可见行数 · log n + 输出量) |
| 亚像素帧合并 + 行采样 + 硬性 quad 预算 | 顶点数有上界，与总帧数无关 |
| 所有矩形合成**一个 Mesh**，一次 draw call | 500 万帧和 5 万帧的绘制调用数一样 |
| mmap 零拷贝 + 无 transform 时多线程分片解析 | 1 GB SVG 约 1.3 s |
| 每个文档常驻一份 `Arc<Scene>` | 标签页切换是 O(1) 的索引改动 |
| 后台线程解析 + 无锁进度 | 打开大文件时 UI 不冻结，可取消 |

## 性能实测

测试环境：Windows 11 / Rust 1.98 (`x86_64-pc-windows-msvc`) / 20 逻辑核心 / `--release`。
测试数据由内置生成器 `--gen` 合成（结构与 `inferno` 输出一致，含背景矩形、`<title>`、`<text>`）。

| 数据集 | 帧数 | 文件大小 | 解析耗时 | 解析吞吐 | 场景常驻内存 | 每帧几何构建 mean / p95 / max | 峰值可见帧 | 峰值 quad 数 |
| --- | ---: | ---: | ---: | ---: | ---: | --- | ---: | ---: |
| `f200k.svg` | 200,000 | 41.3 MB | 64 ms | 650 MB/s | 6.6 MB | 0.01 / 0.05 / **0.11 ms** | 66,183 | 8,344 |
| `f1m.svg` | 1,000,000 | 208 MB | 290 ms | 717 MB/s | 32.2 MB | 0.04 / 0.12 / **0.62 ms** | 84,063 | 8,870 |
| `f5m.svg` | 5,000,000 | 1.05 GB | 1521 ms | 688 MB/s | 160.2 MB | 0.09 / 0.15 / **0.23 ms** | 79,696 | 7,168 |
| `pl_style.svg`（flamegraph.pl 形态） | 23,341 | 8.7 MB | 11 ms | 824 MB/s | 1.0 MB | 0.08 ms（适配全图） | 23,341 | 23,225 |

> 「每帧几何构建」= 视口裁剪 + 生成 quad 列表，在**完整缩放范围**（1× 到 200×）上扫描 300–400 次取分布，每次迭代都重建几何。它是交互时每帧都要跑的热路径。
> 实测运行中状态栏显示 **121–141 fps**（该环境下 vsync 未限帧）；几何构建在 500 万帧时最大 0.39 ms，占 60 fps 预算的 2.3%。

```powershell

.\target\release\flamereader.exe --gen testdata\f5m.svg 5000000   # 生成 500 万帧测试图
.\target\release\flamereader.exe --bench testdata\f5m.svg 300      # 跑基准
```

## 快速开始

### 环境要求

- **Rust** stable（本项目在 1.98 上验证）
- **Visual Studio Build Tools**，勾选「使用 C++ 的桌面开发」（提供 `link.exe` 与 Windows SDK）
- Windows 10 / 11

> 只有 msvc 目标需要 link.exe。若 cargo build 报 “linker `link.exe` not found”，说明没有找到 MSVC 链接器，请安装 Build Tools，或在「Developer Command Prompt」里构建。

### 构建与运行

```powershell
# 开发构建（编译快）
cargo run --release -- sample.svg

# 发布构建
cargo build --release
.\target\release\flamereader.exe sample.svg

# 可选：连启动瞬间的那一下控制台闪现也去掉（代价见下）
cargo build --release --features gui
```

直接双击 `flamereader.exe` 会打开欢迎页，可以按钮选文件，也可以把 `.svg` / `.svg.gz` **拖进窗口**。

### 关于那个黑色控制台窗口

程序以 console 子系统链接，这样 `--selftest` / `--bench` / `--gen` 才能往终端输出。代价是双击启动时 Windows 会分配一个控制台黑框。所以启动时做了一次判断（见 `main.rs` 的 `detach_console_for_gui`）：

| 启动方式 | 行为 |
| --- | --- |
| 双击 / 从资源管理器启动（控制台是本进程独占的） | **调用 `FreeConsole()` 释放掉**，没有黑框 |
| 从终端启动（`flamereader --selftest f.svg`） | 保留控制台，正常打印 |
| 从终端启动且带了**任意** `-` 开头的参数 | 保留控制台 |
| 从终端启动 GUI（`flamereader f.svg`） | 控制台属于该终端，**不动它**（否则会把你的终端窗口关掉） |

判断依据是 `GetConsoleProcessList()`：附加到该控制台的进程数 > 1 说明它是从终端继承来的。

如果连启动瞬间那一帧的黑框闪现都不想要，用 `--features gui` 构建成 windows 子系统程序；代价是此后 CLI 模式不再有任何输出。

## 技术架构

### 整体分层

```
┌──────────────────────────────────────────────────────────────┐
│ main.rs        CLI 解析 / eframe 启动 / selftest / bench      │
├──────────────────────────────────────────────────────────────┤
│ app.rs         应用外壳：标签页、工具栏、面包屑、详情、快捷键    │
│ view.rs        图形控件：输入 → 视口变换 → Mesh、标签、提示      │
│ palette.rs     颜色：SVG fill 解析 + namehash 调色板            │
├──────────────────────────────────────────────────────────────┤
│ lod.rs         ★ 视口裁剪 + LOD → 屏幕空间 quad 列表（无 GUI 依赖）│
│ scene.rs       ★ 扁平场景模型 + 层级索引 + 二分裁剪/命中/统计    │
├──────────────────────────────────────────────────────────────┤
│ svg.rs         ★ 手写字节扫描解析器（串行 / 分片并行）           │
│ loader.rs      后台线程加载（mmap / gunzip）+ 进度 + 取消        │
│ progress.rs    无锁进度（原子量）                              │
│ search.rs      rayon 并行子串搜索 + top-K                      │
│ gen.rs         合成火焰图生成器（测试数据 / 基准）               │
└──────────────────────────────────────────────────────────────┘
```

关键设计：**`lod.rs` 和 `scene.rs` 完全不依赖 GUI**。整条热路径（裁剪 → 几何）可以在没有窗口的情况下被基准测试和单元测试覆盖，渲染层只是把 quad 列表翻译成 Mesh。

### 数据模型

```rust
#[repr(C)]
pub struct Frame {
    pub x: f64,     // 图坐标左边界
    pub w: f64,     // 宽度
    pub y: f32,     // 行坐标（深度 × 行高）
    pub h: f32,     // 行高
    pub color: u32, // 0xRRGGBB，来自 SVG fill 或调色板
    pub name: u32,  // 名字表下标
}
```

- **32 字节定长**，全部帧连续存在一个 `Vec<Frame>` 里 —— 顺序访问对 CPU 缓存友好，500 万帧只要 160 MB。
- **帧名去重**：5,000,000 帧只有 4,097 个唯一名字，`Scene::names` 存名字表，帧里只存下标。搜索时字符串匹配只需跑 4,097 次，而不是 500 万次。
- **层级索引**：

```rust
pub struct Level {
    pub y: f32,
    pub h: f32,
    pub frames: Range<u32>,   // 指向 Scene::frames 的连续区间
}
```

`Scene::build()` 把帧按 `(y, x)` 排序（`total_cmp`，NaN 安全），再把相同 `y` 的帧切成 `Level`。**行内 x 单调递增**是后面所有二分查找的前提。

### 视口裁剪：O(log n + k)

这是整个查看器性能的核心。给一个视口矩形，要拿到所有可见帧：

```rust
// 1) 纵向：哪些行与 [gy0, gy1] 相交
let levels = scene.levels_in_range(gy0, gy1);          // 一次二分

// 2) 横向：行内哪些帧与 [gx0, gx1] 相交
let range = scene.frames_in_level(li, gx0, gx1);       // 两次二分
```

```rust
pub fn frames_in_level(&self, level: usize, x0: f64, x1: f64) -> Range<usize> {
    let l = &self.levels[level];
    let s = &self.frames[l.frames.start as usize..l.frames.end as usize];
    let lo = s.partition_point(|f| f.x + f.w < x0);   // 结束于 x0 之前的帧
    let hi = s.partition_point(|f| f.x <= x1);        // 起始于 x1 之后的帧
    l.frames.start as usize + lo..l.frames.start as usize + hi.max(lo)
}
```

代价只与**可见帧数量**有关，与总帧数只有两次log n 的关系。任何缩放级别下，屏幕上能画出来的东西都被像素数限制住了，所以这个值有天然上界。

命中测试（鼠标位置 → 帧）用同一套索引：先二分找行，再二分找帧。

### 细节层级（LOD）

即使用户缩到「全图可见」，也不能真去画 500 万个亚像素矩形。三层降级：

1. **横向合并（按颜色分段）**：屏幕宽度 < `MIN_RUN_PX`（0.34 px）的连续帧合并成一条 run。合并**不能只留一个颜色** —— 那样几百个帧会塌成一条纯色长条，看起来像一个节点，而且"放大后长条就没了"，因为帧不再需要合并。所以颜色变化会开启新的合并段，但要求当前段已经有 `MERGED_SEGMENT_PX`（3 px）宽：密集区的颜色结构得以保留，额外顶点数被限制在"每几像素一个"的量级（每行 ≤ 屏宽/3）。`per_row` 预算会先扣掉这个上界，保证 `dropped` 仍然为 0。
2. **纵向跳行**：行高 < `MIN_ROW_PX`（1.2 px）时，按 `ceil(1.2 / 行高)` 的步长采样行。
3. **硬预算**：每帧 quad 数不超过 `budget`（默认 120,000，UI 可调）。每行的合并阈值由 `budget / 可见行数` 反推，保证任何情况下都不会超预算 —— 基准测试里对每次迭代都断言 `stats.dropped == 0`。

4. **行间隔保底**：相邻行的矩形边界本来只差文档自己那点行距，缩小时它很容易掉到一个像素以下。抗锯齿会把两行的边缘混起来，整张图看起来"糊"成一片色块。所以每行按屏幕像素内缩一点：行高 > 4 px 时内缩 `clamp(行高 × 0.15, 0.6, 1.0)` 像素，高倍率下最多 1 px（不喧宾夺主），低倍率下保证看起来是"行"而不是一块斑。行高 ≤ 4 px 时不内缩 —— 否则会把这些已经很细的行直接擦掉。描边和标签裁剪用同一个内缩量，保证"画出来的"和"框住的"是同一条带。
5. **列间隔保底**：同一行里相邻帧在源文件里是**严丝合缝**的 —— 让它们看得出分界的是原始 SVG 的 `rx="2"` 圆角，在边界处露出背景。为了把顶点数控制住，渲染器画的是直角矩形（见「已知限制」），于是两个同色相邻帧会连成一条不间断的长条，缩得越小越明显。所以每帧左右各内缩 `clamp(屏幕宽 × 0.05, 0.3, 0.5)` 像素：帧宽 > 3 px 时给出一条约 1 px 的暗缝，≤ 3 px 时不内缩（那点宽度本来也分不出两帧，交给横向合并）。同一个内缩量也用在悬停描边和标签裁剪上。

还有一个「可读性钳制」：如果按宽度适配后**行高不足 3 px**（超大图常见），就把缩放钳到行高 3 px，并把**根行钉在行生长方向的远端**（未翻转时是顶部，翻转后是底部），这样打开大图不会看到一条 1 px 的细缝。

### 解析器

火焰图 SVG 是机器生成的、格式极其规整，所以没有用通用 XML DOM，而是**手写字节扫描器**（`svg.rs`）：

- `memchr` 定位 `<`，状态机分派 `<g>` / `<rect>` / `<title>` / `<text>` / 注释 / CDATA / DOCTYPE / 处理指令。
- 属性解析是零分配的字节切片扫描，`for_each_attr` 直接把 `(name, value)` 交给闭包。
- 浮点解析是手写的（`parse_f64`），不走 `str::parse`，并容忍 `px` 之类的尾缀。
- `<title>` 自带 `"foo (1234 samples, 12.34%)"` 的统计后缀，会被 `strip_stats` 剥掉，得到干净的函数名。
- `<g>` 的 `transform`（`translate` / `scale` / `matrix` / `rotate`）用 2×3 仿射矩阵栈累积；矩形按变换后的包围盒处理。
- XML 实体（`&amp;` / `&#x4e2d;` …）按需解码，绝大多数名字里没有 `&`，走借用快路径。
- 长名字默认取 `<title>`（完整名），没有 `<title>` 时退回到后续 `<text>` 的内容。

**并行策略**：先扫描整个缓冲区找 `transform`。
- **不含 transform**（`flamegraph.pl` / `inferno` 输出的绝大多数情况）：把 1 GB 缓冲区按 `<title` 对齐切成 N 片，rayon 并行解析，每片本地做名字 intern，最后合并并重映射名字下标（每片只对**唯一名字**做一次映射，不是每帧）。
- **含 transform**：退化成一个线程顺序扫描（因为分片会丢失 `<g>` 的继承状态），保证正确性。

其他细节：

- **零拷贝**：文件直接 `mmap`，解析器在映射内存上工作。`.svg.gz` 走 `flate2` 流式解压。
- **背景矩形清理**：`inferno` 之类会加一个无标题的全宽背景 `<rect>`，会被识别并剔除，否则它会变成一根假的根帧。`flamegraph.pl` 的背景用 `fill="url(#background)"`，走的是另一条路 —— 见下一条。
- **无法解析的 paint 不是帧**：`fill="none"` 和 `fill="url(#...)"`（渐变/图案引用）都会让矩形被跳过。曾经这里回退成了默认灰色，后果很严重：背景矩形会变成一帧，而它「高」等于整幅画布，行分组容差又是「帧高的一半」，于是**后面所有行被合并成一个巨大 level**，画面表现为竖直色带贯穿整个高度。`--selftest` 的行数与重叠断言能抓到它。
- **标签 `<text>` 只在同一个 `<g>` 内生效**：生成器会在图外放 `<text id="title">`、`<text id="search">` 之类的独立文本。如果不加限制，一个没有 `<title>` 的矩形（比如背景）会「捡到」紧随其后的 `Flame Graph` 当名字，从而绕过背景剔除逻辑。解析器用 `group_depth` 把标签限定在 `<g>` 内部。
- **行分组容差取全局最小帧高**：这样单个异常矩形（超宽/超高）无法撑大容差、吞掉相邻行。
- **零尺寸矩形统计**：宽度被舍入成 `0.000` 的矩形是看不见也点不到的，会被跳过并**如实计数**（`--selftest` 会报告），而不是悄悄丢掉。
- **无锁进度 + 取消**：`Progress` 全是原子量，加载线程写、UI 读，不阻塞；`AtomicBool` 支持中途取消。

### 坐标精度：一个真实的坑

最初帧坐标用 `f32` 存。自检发现 500 万帧的图里最大「同层重叠」高达 **1795 个图坐标单位**，远超任何舍入误差。

追查过程：把生成器的输出和解析结果逐一比对，发现生成器写的是**像素级精确平铺**的数据：

```
x=696790.4861 w=0.0422  ->  ends at 696790.5283
x=696790.5284 w=1795.9584
```

两帧严丝合缝。但 `f32` 在 696790 附近的 ULP 是 **0.0625**，比 `0.0422` 还大 —— 于是两帧被量化到**同一个 x**，排序后窄帧看起来「陷进」了宽帧内部，重叠量就等于宽帧的整个宽度。

结论：**500 万帧 / 125 万单位画布上，帧间距可以小到低于 `f32` 的相对精度（6e-8）**，`f32` 从原理上就存不下。修复方案是把**图坐标改成 f64**（`x`、`w`），而**屏幕坐标保持 f32**（像素永远不需要更高精度）。改完之后最大重叠降到 `0.0001` —— 正好等于 SVG 文本本身的 4 位小数精度。

代价：`Frame` 从 24 字节变 32 字节，500 万帧 160 MB。这个取舍是值得的。

### 视口变换与纵向翻转

```rust
pub struct Viewport {
    pub pan_x: f64,
    pub pan_y: f64,
    pub scale: f64,     // 图单位 -> 像素
    pub flip_y: bool,   // 行方向镜像
}
```

- `sx / sy`：图坐标 → 屏幕坐标；`gx / gy`：反向。
- 翻转通过 `dir = ±1` 织进同一组仿射公式：`sy(gy) = (dir·gy + pan_y)·scale`，`gy(sy) = dir·(sy/scale − pan_y)`。裁剪、命中、标签、描边全部自动跟随，只有「帧矩形」需要归一化 `min/max`（因为翻转后顶边在底边下方）。
- `zoom_at(screen_x, screen_y, factor)` 保证光标下的图点不动 —— 这是滚轮缩放「跟手」的关键，单元测试直接断言这一点。
- **`root at bottom`**：`Scene::build` 时记录最宽帧（根）位于上半还是下半，得到 `root_at_top`。显示时 `flip_y = 用户想要根在底部 && 文档本身根在顶部`。所以已经根在底部的文件不会被翻错，选项是幂等的。

### 子树聚焦

需求是「点一帧，只看它的子进程」。实现上没有复制或重建场景 —— 因为**一棵子树在每一行上都占据一段连续的 x 区间**，所以聚焦只是两个约束：

```rust
pub struct Focus { pub frame: u32, pub x0: f64, pub x1: f64, pub y0: f32, pub level: usize }
```

```rust
// 1) 把横向裁剪窗口与子树区间求交
if let Some(f) = focus { gx0 = gx0.max(f.x0); gx1 = gx1.min(f.x1); }
// 2) 行索引加一个下界：子树不含更浅的行
let levels = all_levels.start.max(f.level)..all_levels.end;
```

复杂度 **O(1)**，不需要重建场景、不需要额外的索引、对 500 万帧和 5 万帧一样快。

**父层级保留但虚化 —— 而且只保留依赖路径。** 只按上面的约束裁剪，父层级会整个消失，用户就失去了「我在哪儿」的参照。但把**聚焦行以上的所有整行**都画成虚化也不行：那会形成一大片横贯全宽的暗色板，把真正要看的子树埋掉。所以虚化趟只走**从根到聚焦帧的那条路径**：

```
虚化趟：Scene::ancestry(focus) 上的每一帧 → out.faded（+ 同名标签），渲染时 alpha 52 混合
原色趟：聚焦行到图底，x 裁剪到 [x0, x1]   → out.quads + out.labels
```

虚化趟是 **O(depth)** 而不是 O(行数)：调用栈一般只有几十层，所以上下文只花掉几十个矩形，不参与 quad 预算。原色趟仍然走完整的 LOD 与预算机制。两段几何写进**同一个 Mesh**，仍然只有一次 draw call：虚化的矩形以 `Color32::from_rgba_unmultiplied(..., 52)` 作为顶点色，egui 用预乘 alpha 混合，直接叠在面板背景上。

**虚化的节点保留名字。** `LabelReq` 带一个 `faded` 标记，虚化路径上的帧照常排文字，只是换成一个偏亮的半透明色（那些矩形已经混进深色背景，再用「对比色」会看不见）。没有名字的虚化矩形是无法辨认的，上下文也就没用了。

**取景框必须同时容纳子树和路径。** 这一步有两个容易写错的地方，都踩过：

- **纵向终点要用子树的真实深度，不能用全图最深处。** 一棵子树往往在好几行之前就结束了，而全图还在往下延伸。用 `scene.max_y` 会让适配为一个 4 行的子树预留 36 行的垂直空间 —— 内容被压到视口一角、其余全是空白。新增的 `Scene::subtree_max_y()` 沿着「子树在每一行占据连续 x 区间」这个性质往下走，走到某一行在该区间内没有帧为止，得到真实深度。**O(深度 · log n)**，只在点击时算一次。
- **纵向起点要回到根行，而不是聚焦行。** 否则一点击，解释「这个节点为什么存在」的上下文全部出框。现在取景范围 = `[scene.min_y, subtree_max_y]`，父层级路径和子树一起入框。

**命中测试必须和"画了什么"逐字一致。** 这里踩过一次坑：最初的门控写成「在聚焦行**以上**就放行」，本意是放行虚化的父层级，结果是父层级那一行里的**所有兄弟节点**都被放行了 —— 它们其实早被裁掉没画。表现就是鼠标在子树周围的空白处滑动时，仍然会高亮出根本不存在的帧和浮层。现在把判定抽成一个纯函数 `lod::is_focused_visible()`：只有在**依赖路径上**、或者**落在子树区间内**的帧才可交互，和两个绘制通道的选择条件完全对应。

点击虚化的父层级即可回到那一层，配合面包屑形成双向导航；聚焦状态下点击空白不会再清掉当前选中的帧。

聚焦后视图会重新适配到这棵子树；面包屑栏由 `Scene::ancestry()`（沿 `mid_x` 向上找父帧）生成。

> **一个值得记下来的时序坑。** 最初 `show()` 把「重新适配视口」放在**输入处理之前**：点击在这一帧把 `initialized` 置 false，但这一帧的几何仍然用旧视口算出来；而 egui 只在有输入时重绘，于是**画面会一直停在那个错误帧上，直到你动一下鼠标**。表现就是「点了之后看到的不是子树」。修法是把适配挪到**输入之后、构建几何之前**，这样用户看到的第一帧就已经是对的。凡是「状态变更 → 需要重新布局 → 立即绘制」的即时模式 UI，都要小心这个顺序。

### 渲染管线

- 所有可见矩形写进**同一个 `egui::Mesh`**（每个 quad 4 顶点 / 6 索引），最后一次 `painter.add(Shape::mesh(mesh))`。绘制调用数与帧数无关。
- **标签**：只为「屏幕宽度 ≥ 26 px 且行高 ≥ 9 px」的帧排布文字，字体大小跟着行高走，整体预算 400 个并按可见行数分摊；文字用 `with_clip_rect` 裁到帧矩形内，不会溢出到邻居上。egui 自带的 galley 缓存对重复函数名很有效。
- **悬浮提示**是自绘的（`layout_no_wrap` + 填充矩形 + 描边），不走 egui 弹窗，避免额外的布局/层级开销。
- **搜索高亮**只给前 400 个命中画描边，当前命中用更粗的黄色框。
- 采样：`stats` 实时暴露 `rows_visited / rows_drawn / row_step / frames_considered / frames_drawn / frames_merged / quads / dropped`，状态栏直接显示，便于自证没有超预算。

## 已知限制

- **`rx` / `ry` 圆角被忽略**：矩形按直角绘制。这是刻意的性能取舍（每个圆角矩形要多几十个顶点）。代价是原始 SVG 靠圆角在帧之间露出的那道缝没有了，所以改为给每帧左右各留一条约 1 px 的亚像素缝（见「细节层级」第 5 层），保证相邻帧在低倍率下也不会连成一条。
- **渐变/图案填充不渲染**：`fill="url(#...)"` 这类引用式 paint 无法解析，对应矩形会被**跳过**（而不是涂成灰色）。火焰图工具几乎都用 `rgb(...)`，影响很小。但这一点很关键：`flamegraph.pl` 的背景矩形正是 `fill="url(#background)"`，如果把它当成普通帧，它会以「整幅画布那么高」的一帧存在，并靠行分组容差把下面所有行吞掉。
- **含 `transform` 的文档退化为单线程解析**：正确性优先。这类文件在实际火焰图输出中很少见。
- **路径压缩 / 上下文菜单 / 导出**：暂未实现。
- 超大图（>5000 万帧）会把场景内存推到 GB 级，此时建议先按需裁剪 SVG。

## 实现要点小结

如果只记三件事：

1. **把「文档」和「视图」彻底分开**：解析一次得到不可变扁平数组，之后每一帧只做二分裁剪 + 生成 quad。
2. **给输出加硬上界**：LOD 合并 + 行采样 + quad 预算，让顶点数与总帧数脱钩，而不是靠「应该够快」。
3. **把热路径做成无 GUI 依赖的纯函数**：因为 `lod.rs` 不碰窗口，它才能被基准测试和单元测试覆盖 —— 本文里所有性能数字和抓到的那几个渲染缺陷，都是这么来的。
