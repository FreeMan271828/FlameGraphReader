# FlameReader

面向**超大火焰图**的 Windows 桌面查看器：1 GB 的 SVG 打开不卡，缩放平移稳定 120+ fps。

Rust + `egui`/`wgpu`，单文件免安装。

---

## 背景：浏览器为什么看大图会卡

火焰图通常由 `flamegraph.pl` / `inferno` 生成，输出是几万到几十万行的 SVG：

```xml
<svg>
  <rect x="0" y="0" width="1200" height="16" fill="rgb(230,60,40)"/>
  <text x="3" y="12">main</text>
  ...
</svg>
```

浏览器渲染它有三个绕不开的代价：

1. **DOM 就是数据本身。** 50 万个 `<rect>` 就是 50 万个 DOM 节点，每个都带样式、布局、合成开销，内存和重排成本随帧数线性增长。
2. **每次缩放都在改样式。** 要么触发整棵子树重排重绘，要么给每个节点更新 `transform`，交互延迟完全被节点数绑死。
3. **节点数没有上界。** 5 万帧还能忍，500 万帧（1 GB 文件）直接卡死。

FlameReader 把这三点全部去掉：**帧数只影响一次解析，之后的所有交互只和屏幕像素有关**。

## 作用

- 打开 `.svg` / `.svg.gz` 火焰图，滚轮缩放、拖拽平移，500 万帧依然流畅
- 点击任意帧**下钻**：只显示该帧及其子树，同时保留从根到它的依赖路径（虚化），点击虚化层级可退回那一层
- 按帧名搜索，命中在图上标出；导航可在「保持视图」和「跳转到节点」之间切换
- 多标签页，切换是 O(1)（每个文档常驻一份场景，不用重新解析）
- 后台解析 + 无锁进度，打开大文件时界面不冻结，可取消

## 原理

四个决定性的设计。

### 1. 丢掉 DOM，压成扁平数组

手写字节扫描器直接在 `mmap` 上解析 SVG（不用 XML 库），每个 `<rect>` 压成 32 字节：

```rust
#[repr(C)]
struct Frame {
    x: f64,      // 图上坐标用 f64：大图总宽可达 1e6，f32 缩放时会抖
    w: f64,
    y: f32,
    h: f32,
    color: u32,
    name: u32,   // 名字去重后只存下标：500 万帧只有 4097 个唯一名字
}
```

解析吞吐 **650–1150 MB/s**，1 GB 文件 1.3 秒解析完，常驻 160 MB。

### 2. 视口裁剪是 O(log n)

行内帧按 x 排序，裁剪时先二分定位可见行区间，再在行内两次二分取 x 区间。与总帧数只有两次 `log n` 的关系，剩余代价正比于**可见帧数**，而可见帧数被像素数天然限制住。

### 3. 顶点数有硬上界

屏幕宽 < 0.34 px 的连续帧合并成一条 run；行高 < 1.2 px 时跳行绘制；再加一个硬性 quad 预算（默认 12 万）。于是 500 万帧和 5 万帧的顶点数是同一个量级：

| 数据集 | 峰值可见帧 | 峰值 quad |
| --- | ---: | ---: |
| 20 万帧 | 66,183 | 8,344 |
| 500 万帧 | 79,696 | 7,168 |

### 4. 一个 Mesh，一次 draw call

所有矩形（含虚化通道）写进同一个 `Mesh`。几何构建 0.1–0.6 ms，占 60 fps 预算的 2% 以内。普通缩放平移不重建场景，只重算视口变换。

> 两个值得记下来的坑，代码注释里也有：
> 图上坐标必须用 `f64` —— `f32` 在总宽 1e6 时精度不够，缩放会跳变；
> 聚焦后重新适配视口必须发生在**输入处理之后、构建几何之前** —— egui 只在有输入时重绘，顺序反了画面会停在错误的帧上，直到鼠标移动才恢复。

## 性能实测

Windows 11 / Rust 1.98 (`x86_64-pc-windows-msvc`) / 20 逻辑核心 / `--release`。
测试数据由内置生成器 `--gen` 合成，结构与 `inferno` 输出一致。

| 数据集 | 帧数 | 文件大小 | 解析 | 吞吐 | 常驻内存 | 每帧几何构建 max |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `f200k.svg` | 200,000 | 41.3 MB | 64 ms | 650 MB/s | 6.6 MB | 0.11 ms |
| `f1m.svg` | 1,000,000 | 208 MB | 290 ms | 717 MB/s | 32.2 MB | 0.62 ms |
| `f5m.svg` | 5,000,000 | 1.05 GB | 1521 ms | 688 MB/s | 160.2 MB | 0.23 ms |
| `pl_style.svg` | 23,341 | 8.7 MB | 11 ms | 824 MB/s | 1.0 MB | — |

「每帧几何构建」= 视口裁剪 + 生成 quad，在完整缩放范围（1× 到 200×）上扫描数百次取最大值。这是交互时每帧都要跑的热路径，也是这个项目真正的性能指标。

## 使用方式

### 环境要求

- Rust stable（本项目在 1.98 上验证）
- Visual Studio Build Tools，勾选「使用 C++ 的桌面开发」（提供 `link.exe`）
- Windows 10 / 11

### 构建与运行

```powershell
cargo build --release
.\target\release\flamereader.exe sample.svg
```

双击 `flamereader.exe` 会打开欢迎页，可以按钮选文件，也可以把 `.svg` 直接拖进窗口。

### 命令行

```
flamereader [OPTIONS] [FILE.svg ...]

  （无参数）                  打开 GUI
  FILE.svg ...                在 GUI 中打开这些文件

  --gen <out.svg> <frames>    生成合成火焰图并退出
  --selftest <file.svg>       解析 + 数据完整性校验 + 统计，然后退出
  --bench <file.svg> [n]      在完整缩放范围上测量裁剪/建网格耗时
  --smoke <file.svg> [n]      实际渲染 n 帧并报告帧率
  --serial                    强制单线程解析
  --chunks                    打印每个解析分片的字节范围与帧数
  -h, --help / -V, --version
```

生成并自检一张 500 万帧的图：

```powershell
.\target\release\flamereader.exe --gen testdata\f5m.svg 5000000
.\target\release\flamereader.exe --selftest testdata\f5m.svg
```

程序以 console 子系统链接，所以 `--selftest` 之类能正常往终端输出。GUI 启动时会自行释放 Windows 分配的控制台窗口，**双击不会有黑框**。

### 交互

| 操作 | 行为 |
| --- | --- |
| 滚轮 / 拖拽 | 以光标为中心缩放 / 平移 |
| **单击一帧** | 下钻：**保持当前缩放**，该帧移到视口正中，子树按原色展开 |
| **单击虚化的父层级** | 回到那一层 |
| 右键 | 回到全图 |
| 面包屑 | 点任意祖先回到那一层 |
| `n` / `p` | 上一个 / 下一个搜索命中 |
| `0` / `F` | 适配全图 |
| `+` / `-` | 缩放 |
| 方向键 | 平移 |
| `Esc` / `Backspace` | 逐级退出（先退聚焦，再清选中） |
| `Ctrl+O` / `Ctrl+W` | 打开 / 关闭标签页 |
| `F1` | 快捷键帮助 |

右侧详情面板显示选中帧的 total/self 占比、调用路径和子帧列表；搜索面板列出命中，可逐条跳转。

## 测试

```powershell
cargo test
cargo fmt --check
cargo clippy --release --all-targets
```

29 个单元测试，覆盖几何热路径与解析器的关键不变量：

- quad 数永不超预算，`dropped == 0`
- 视口不在屏幕原点时图仍完整落在视口内；显式「适配全图」必须真的放下整张图
- 聚焦后子层级确实展开、虚化集合精确等于调用路径
- **可交互范围与实际绘制范围逐字一致**（虚化路径可点，被裁掉的帧一个都不可点）
- 相邻行、相邻帧之间必定留有可见间隔（否则缩放变小就会糊成一片）
- 文本框获得焦点时，快捷键必须让位给输入

另有 3 个针对真实 SVG 格式的解析回归测试：渐变背景不是帧、独立 `<text>` 不给矩形命名、`fill="none"` 跳过而缺失 `fill` 照画。

## 已知限制

- **忽略 `rx` / `ry` 圆角**：矩形按直角绘制，这是为了让顶点数有界。代价是原 SVG 靠圆角在帧之间露出的那道缝没了，改为给每帧左右各留约 1 px 的亚像素缝。
- **含 `transform` 的 SVG 走单线程**：分片解析会丢失 `<g>` 的继承状态，因此退化为顺序扫描以保证正确性。
- **搜索上限 20,000 条命中**：超出部分不列出。
- **仅 Windows**：控制台分离用了 kernel32 的 `FreeConsole`。
